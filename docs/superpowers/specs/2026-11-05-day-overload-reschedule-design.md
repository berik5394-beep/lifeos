# Перегруз дня → робот предлагает сдвинуть график (одно касание) + цели месяца/года

**Дата:** 2026-11-05.

**Решения Berik:**
- лишняя задача на день, где не хватает времени, сдвигает весь график;
- загорается предупреждение, что цели месяца и года меняются;
- «каждый инструмент обращается ко всем», без пересечений в интересах;
- как двигать: **робот предлагает, юзер подтверждает одним касанием** (2026-11-05).

## Что есть сейчас (аудит, проверено в коде)
- `create_task` (только чат) после создания добавляет строку «день/неделя/месяц перегружен» (`day-load`, `week-load`, `month-load`):
  - это только текст «Перенести «X» на завтра?», ничего не двигается;
  - **баг:** день проверяется всегда СЕГОДНЯШНИЙ (`create-task.ts:70` → `new Date()`), а не день задачи. Задача на перегруженное «завтра» молчит;
  - дедуп: не больше одной строки в день.
- `POST /tasks` (карточка «Задачи» в комнате) и `create_event` нагрузку не проверяют вообще.
- Двигает задачи только `defer_overdue` (просрочки → сегодня, с подтверждением).
- Влияние на цели — только денежное (`goal-impact`); про время и цели месяца/года предупреждения нет.
- Механизм «одного касания» уже есть: `PendingAction`, кнопка «Подтвердить» в облачке робота и в чате, `/voice/confirm-action`, TTL 5 мин. Так работают деньги и `defer_overdue`.

## Часть A. Как это выглядит

1. Юзер добавляет задачу (голосом, текстом роботу или в карточке «Задачи») на день, где времени не хватает.
2. Задача **создаётся сразу**: добавление не блокируем.
3. Робот отвечает в облачке:

   > День четверга перегружен: задач на ~7 ч, свободно ~5 ч.
   > Предлагаю:
   > • «Разобрать почту» → пятница
   > • «Позвонить в банк» → понедельник
   > ⚠️ «Час английского» — шаг к цели года «Английский B2» — уходит на следующую неделю: цель недели «3 урока» не закрывается, цель месяца под угрозой.
   >
   > [Подтвердить] [Отмена]

4. «Подтвердить» — задачи переезжают; робот: «Готово, график сдвинул. Цель «Английский B2» — догоним в выходные?» «Отмена» — ничего не трогаем, предупреждение остаётся в ответе.

## Часть B. Как считаем предложение (сервер, чистая функция `planShift`)

**Вход:**
- день задачи D;
- задачи D (минуты = `estimatedMinutes ?? 30`, важность);
- свободное время D:
  - окно 09:00–20:00 минус встречи;
  - для «сегодня» — от текущего момента;
- то же для следующих 7 дней.

**Правила:**
- Новую задачу **не двигаем**: юзер только что сам её поставил.
- Не двигаем задачи **со временем** (`time` задан — это договорённость), встречи и **critical**.
- Двигаем наименее важные (`computeCapacityFit` → overflow): сначала low, потом medium, потом high.
- Каждую сдвигаемую ставим на **ближайший день, куда она влезает целиком**, учитывая уже сдвинутые туда. Выходные — так же, как будни (как сейчас считает ёмкость).
- Если за 7 дней места нет, задачу не двигаем и пишем честно: «Неделя забита — на «X» времени нет. Отменить или делегировать?»
- Предложение — не больше 5 переносов (длинный список никто не прочтёт), остальное одной строкой «…и ещё N».

**Цели (предупреждение «меняются цели»):** для каждой сдвигаемой задачи смотрим, к чему она ведёт.
- `planParentType = WeeklyGoal`, перенос за конец недели → «цель недели «…» не закрывается».
- Если у этой недельной цели есть годовая (`planParentId` → YearlyGoal), а сама годовая уже отстаёт по `plan-vs-fact` → «цель года «…» отстаёт ещё сильнее».
- `planParentType = YearlyGoal` → «шаг к цели года «…» сдвигается на N дней».
- После переносов неделя перегружена (`week-load`) → «цели недели под угрозой».
- Месяц перегружен (`month-load`): цели месяца + недельные цели против свободного времени месяца → «цели месяца под угрозой: «…»». Цели месяца пока не связаны с задачами, поэтому называем их списком, без привязки к задаче.

Предупреждение о целях показывается **и тогда, когда переносить некуда**. Ничего не выдумываем: только реальные связи и числа из БД (антифаб).

## Часть C. Где срабатывает (каждый вход — один и тот же движок)
| Вход | Сейчас | Станет |
|---|---|---|
| `create_task` (голос/чат) | строка «перегружен» про сегодня | предложение для дня задачи + цели |
| `POST /tasks` (карточка «Задачи») | ничего | то же; ответ несёт `proposal`, робот показывает облачко |
| `PUT /tasks/:id` со сменой даты | ничего | то же для нового дня |
| `create_event` / `POST /events` | конфликт по времени (флаг) | + предложение, если встреча съела время дня |

- Предложение кладётся в `PendingAction` (`action: 'apply_reschedule'`, `input: { moves: [{ taskId, fromDate, toDate }] }`).
- Подтверждение идёт через существующий `/voice/confirm-action`, поэтому кнопка одна и та же в облачке, в чате и голосом («да»).
- Новый инструмент `apply_reschedule` (`needsConfirm: true`):
  - двигает только свои, ещё не выполненные задачи, которые всё ещё стоят на `fromDate`;
  - если юзер успел передвинуть задачу сам, её пропускаем и честно говорим об этом.
- В мобилке после «Подтвердить» открытая карточка инструмента («Задачи»/«Сегодня») перечитывается.

## Часть D. «Каждый инструмент с каждым», без пересечений интересов
Аудит нашёл пары инструментов, между которыми модель может выбрать не тот на одну и ту же фразу. Чиним описаниями: каждый явно говорит «не я, а …».
- `create_task` ↔ `create_event`: встреча с людьми, местом или временем «с–до» → событие; дело → задача.
- `complete_task` ↔ `complete_habit`: «сделал X» — сначала привычка, если такая есть, иначе задача (как уже решает матчер).
- `create_obligation` ↔ `create_task`: «я обещал X кому-то» → обязательство; «надо X» → задача.
- `remember_entity` ↔ `set_birthday`: «запомни день рождения» → только `set_birthday`.
- `suggest_goal` ↔ `create_monthly_goal`: «цель на месяц: …» → создать; «помоги придумать цель» → предложить.

Плюс eval-тест маршрутизации на эти фразы (как существующие тесты intent).

## Безопасность и честность
- Ничего не двигается без касания. Отмена — ничего не меняет.
- Задача создаётся всегда, даже если расчёт упал: расчёт best-effort, ответ просто без предложения.
- Флаг `FEATURE_V2_RESCHEDULE`. При выключенном флаге всё байт-в-байт как сейчас. По правилу ship → `all` сразу.
- Старый дедуп «одна строка о перегрузе в день» для предложений не действует: каждая лишняя задача — новое предложение. Новое предложение заменяет старое (`PendingAction` — один на юзера).
- Двойной тап / «да» в двух местах: `take()` атомарный, задачи сдвигаются ровно один раз.

## Тесты
- **unit `planShift`:**
  - новая задача не двигается; задачи со временем и critical — тоже;
  - low уходит раньше medium;
  - ближайший день, куда влезает; каскад не перегружает следующий день;
  - нет места на 7 дней → «не влезает»;
  - максимум 5 переносов.
- **unit целей:** перенос за неделю → цель недели; отстающая годовая → строка; без связей → без строки (антифаб).
- **it:**
  - `create_task` на перегруженное ЗАВТРА → предложение (регресс-тест бага «всегда сегодня»);
  - `POST /tasks` → `proposal` + `PendingAction`;
  - confirm → задачи переехали; повторный confirm → 409;
  - задача уже сдвинута вручную → пропущена;
  - флаг off → как раньше.
- **jest (мобилка):** облачко с предложением после добавления задачи в карточке; «Подтвердить» → перечитали задачи.

## Этапы
1. Сервер: `planShift` + цели (чистые) + фикс дня задачи + `apply_reschedule` + `create_task`/`POST /tasks`/`PUT /tasks`.
2. Сервер: события (`create_event`, `POST /events`) + описания инструментов (часть D) + eval-тест.
3. Мобилка: облачко-предложение из карточки «Задачи» и «Сегодня»; перечитать после подтверждения.

## Вне скоупа
- Автоматическая перестановка по времени внутри дня (расписание по часам). Двигаем между днями.
- Связь задач с целями месяца (`MonthlyGoal` не имеет детей). Пока цели месяца называются по перегрузу месяца.
- Делегирование (мост #8).
