# Честный ввод денег (Honest Money Entry)

**Дата:** 2026-06-02
**Статус:** дизайн одобрен Berik (ждёт ревью спеки)
**Тип:** фикс бага доверия #189 (бот сочиняет запись денег). Server-only (packages/server).

## 1. Проблема и корневая причина (доказано: код + прод-БД)

Прод: Berik «я потратил 100 000» → «компьютер» → «да» → бот ответил «Записываю расход 100 000 🖥️… за месяц 235 000» — но **в БД записи НЕТ** (реальный MTD 135 000; «компьютер»/«наушники 25000» выдуманы). Тогда как «потратил 15000 на одежду» (одним сообщением) — записалось.

Цепочка (systematic-debugging):
1. Детерминированный money-prefilter `intent-parser.ts:132,143` заякорен `^(?:запиши\s+)?(?:расход|потратил…)` → требует money-слово в НАЧАЛЕ. «**я** потратил 100000» (ведущее «я») не матчится.
2. Claude-слой парсера тоже не выдал confirm-able `add_expense` (спросил категорию разговором).
3. Сообщение ушло в agent/chat-путь. Там `add_expense` (needsConfirm:true) ИСКЛЮЧЁН из инструментов агента (money-safety) → LLM может только НАРРАТИВИТЬ запись, реально не вызвав tool → **сочиняет** подтверждение + цифры.
4. Многошаг («100000»→«компьютер»→«да») вообще не доходит до confirm-FSM: ни одно сообщение по отдельности не парсится в `add_expense`; «да» без pending → chat → галлюцинация.

Код это уже частично знает: комментарий SSOT Step 6 (`intent-parser.ts:121-128`) — «удаление regex провалилось: чат-агент ВЫДУМАЛ запись, в БД 0 строк». Prefilter вернули, но он недостаточно надёжен (якорь) и не покрывает многошаговый ввод.

## 2. Принцип

Деньги (расход/доход) **ВСЕГДА** проходят детерминированный confirm-FSM (или честный отказ). Разговорный/agent-путь денег НЕ касается. Это уже заявленный инвариант (money-safety) — фикс делает его **дырявость → герметичность**.

## 3. Компонент 1 — Надёжный детект суммы (чистая функция)

Выносим детект денег в экспортируемую чистую `detectMoneyIntent(text): MoneyIntent | null` в `intent-parser.ts` (тестируется напрямую), `parseIntent` зовёт её первой.

```ts
export type MoneyIntent =
  | { action: 'add_expense'; amount: number; category?: string }
  | { action: 'add_income'; amount: number; source?: string };
```

Изменения против текущих регекспов:
- **Ведущие слова до money-слова:** префикс `(?:[а-яё]+\s+){0,3}?` перед ключевым словом → ловит «я потратил», «сегодня купил на», «вчера потратил». `[а-яё]` (НЕ `\w` — кириллица, урок прошлых багов).
- **НЕ дефолтим категорию в 'other'.** Если категория/источник не указаны — поле **отсутствует** (undefined), чтобы оркестратор отличил «нет категории» (→ доспросить) от явной. Запись в `other` (если так и не указали) делает сам tool/слот-филл по дефолту при коммите.
- Консервативность сохраняется: нужен money-глагол (потратил/расход/трата/купил/потрачено · доход/получил/заработал/зарплата/премия) + число. Голое «100000» без глагола НЕ ловим (ложные срабатывания на любые числа). Второй паттерн «5000 на еду» (число+«на»+текст) остаётся.

Примеры (unit):
| Вход | Выход |
|---|---|
| «потратил 15000 на одежду» | expense 15000, category 'одежду' |
| «я потратил 100000» | expense 100000, **category отсутствует** |
| «сегодня купил на 3000 продукты» | expense 3000, category 'продукты' |
| «5000 на такси» | expense 5000, category 'такси' |
| «я получил зарплату 350000» | income 350000, source отсутствует |
| «доход 50000 от фриланса» | income 50000, source 'фриланса' |
| «100000» | null (нет глагола) |
| «какие задачи на сегодня» | null |

## 4. Компонент 2 — Доспрашивание слота через FSM (детерминированно, без LLM)

Когда сумма есть, а категория (расход) / источник (доход) — нет.

**Хранилище:** durable `PendingAction` (Postgres, уже есть). Состояние слот-филла — в `input` JSON: `__awaitingCategory: true` (или `__awaitingSource: true`). **Миграции НЕ нужно.**

**Поток (расход; доход симметричен):**
1. Оркестратор, ветка EXECUTABLE, `add_expense` без категории → НЕ confirm, а:
   `setPendingAction(userId, 'add_expense', { amount, __awaitingCategory: true }, 'На что потратил {amount}₸? (или «отмена»)')` → вернуть этот вопрос. Детерминированная строка, НЕ LLM.
2. Следующее сообщение, `peekPendingAction` → pending с `__awaitingCategory`:
   - `readConfirmSignal === 'cancel'` → `clearPendingAction` → «Окей, отменил — ничего не записал.»
   - иначе → `category = text.trim()` → `setPendingAction(userId, 'add_expense', { amount, category }, confirmationText('add_expense', {amount, category}))` (обычный confirm-pending, `__awaitingCategory` снят) → вернуть «Записать расход {amount}₸ на {category}? Подтверди — запишу.»
3. «да» → `takePendingAction` → `runConfirmedAction('add_expense', {amount, category})` → реестр (аудит ToolCall) → запись. **Каждый шаг детерминирован — соврать невозможно.**

Если категория уже в исходном сообщении → сразу шаг confirm (как сейчас).

**Точка в коде:** ветка `if (pending)` в `handleMessage` (`:442-459`) получает НОВЫЙ блок ПЕРЕД confirm-логикой: «pending ждёт слот → заполнить/отменить». EXECUTABLE-ветка (`:754+`) для `add_expense`/`add_income` без слота → ставит awaiting-pending вместо confirm.

## 5. Компонент 3 — Структурный запрет вранья

- **Главное (корень):** Компонент 1 ловит деньги детерминированно → они НЕ доходят до агента, который и сочиняет. Это убирает причину.
- **Дешёвая защита (defense-in-depth):** правило в системный промпт агента (`ai/jarvis-prompt.ts`): «НИКОГДА не утверждай, что записал расход/доход/задачу/событие, если в этом ходе не был вызван соответствующий инструмент. Деньги записываются ТОЛЬКО через явное подтверждение.» Мягкий слой, но дешёвый и снижает остаточный риск.

## 6. Краевые случаи

- **`__awaitingCategory` + «да»:** «да» — не категория. MVP: `readConfirmSignal('да')==='confirm'`, но в awaiting-ветке confirm не применяется к слоту; берём текст как категорию → запишет category='да' (странно, но НЕ враньё). Приемлемо для MVP. (Опц. улучшение позже: пере-спросить, если текст пустой/да/нет.)
- **`__awaitingCategory` + новая тема/другой расход:** следующий текст трактуется как категория. Если юзер сменил тему — запишется его фраза как категория (поправимо вручную), НО не соврёт. TTL 5 мин страхует. (Опц.: если текст сам парсится в чёткий другой интент — бросить слот-филл; отложено.)
- **Пустой текст категории** (вряд ли в Telegram) → дефолт 'other' при коммите.
- **TTL:** awaiting-pending живёт 5 мин (lazy expire, как все pending). Протух → следующее сообщение парсится с нуля.

## 7. Симметрия: доход

`add_income` без источника → `__awaitingSource` → «От кого/за что доход {amount}₸? (или «отмена»)» → источник → confirm → «да» → запись. Та же FSM-ветка, slotKey = source.

## 8. Флаг / миграции / совместимость

- **Без флага.** Это фикс бага денег, аддитивный: одношаговые кейсы со словом в начале работают как раньше (Компонент 1 — надмножество старых регекспов; Компонент 2 включается ТОЛЬКО когда слот отсутствует). Страховка — тесты + независимое ревью (как TOOLFIX, тоже без флага).
- **Без миграции** (состояние слот-филла в `PendingAction.input` JSON).
- Money-safety инвариант цел: запись только через confirm («да») → реестр (needsConfirm) → аудит. Слот-филл лишь СОБИРАЕТ вход до confirm.

## 9. Тестирование

- **Pure unit `intent-parser` / `detectMoneyIntent`:** таблица §3 (ведущие слова, без-категории, доход, голое число → null, не-деньги → null).
- **FSM слот-филл (orchestrator, инъектируемый `PendingStore` — без БД):** amount-без-категории → awaiting-pending поставлен + вопрос; ответ-категория → confirm-pending; «да» → запись (runConfirmedAction зовётся с {amount, category}); «отмена» на каждом шаге → сброс. Симметрично income.
- **Structural:** промпт-правило §5 присутствует в jarvis-prompt; EXECUTABLE-ветка ставит awaiting-pending для add_expense/add_income без слота.
- Базовая сюита (2087) зелёная, tsc 0, zero vi.mock.

## 10. Non-goals (осознанно)

- Умный отказ от слот-филла при «смене темы» (re-parse следующего сообщения) — опц. улучшение, отложено.
- Распознавание категории из произвольной речи AI-классификатором — детерминированного текста достаточно.
- Банковские SMS/фото-чеки — отдельные каналы (фото уже есть через vision-finance).
- Другие needsConfirm-инструменты (send_telegram) — вне scope; фикс про деньги.
