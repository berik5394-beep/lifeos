# Сделки — личная воронка продаж с follow-up

Дата: 2026-11-05. Статус: дизайн одобрен Berik («Да, пиши спеку»), спека ждёт ревью.

## Зачем

LifeOS — друг и деловой помощник. Для менеджера продаж (или предпринимателя) главное, чего нет:
воронки сделок и напоминаний «пора сделать шаг по клиенту». Люди-клиенты, обещания, брифы перед
встречей, цели с числом уже есть — сделки встраиваются в них, а не живут отдельно.

## Решения Berik

1. Личная воронка: один человек ведёт свои сделки. Не команда, не руководитель.
2. Ввод голосом/чатом роботу + панель «Сделки» для просмотра и правки руками.
3. Пять фиксированных стадий.
4. Follow-up робот ставит сам (по стадии) + напоминает о «затихших» сделках.
5. План продаж на месяц + «записать доход?» одним касанием при выигрыше.

Выбран вариант А: сделка — отдельная запись, привязанная к человеку-клиенту
(отвергнуты: сделка как вид Obligation — смешивает «я должен» и «я продаю»; сделка как атрибут
Entity — одна сделка на клиента, нет истории).

## Данные (Prisma, миграция аддитивная)

```prisma
model Deal {
  id             String    @id @default(cuid())
  userId         String
  user           User      @relation(fields: [userId], references: [id], onDelete: Cascade)
  personEntityId String?   // клиент; onDelete SetNull — сделка живёт, остаётся personName
  person         Entity?   @relation("EntityDeals", fields: [personEntityId], references: [id], onDelete: SetNull)
  personName     String
  title          String    // «оборудование»; если не назван — «сделка»
  amount         Float?    // только из слов юзера; null = сумма не названа
  currency       String    @default("₸")
  stage          String    @default("new") // new | talks | proposal | contract | won | lost
  stageChangedAt DateTime  @default(now())
  nextStepAt     DateTime? @db.Date        // convA: localDateOnlyUTC
  nextStepText   String?
  lastActivityAt DateTime  @default(now()) // любое упоминание/правка
  closedAt       DateTime?                 // won | lost
  lostReason     String?
  wonIncomeId    String?   @unique         // доход уже записан → не дублируем
  createdAt      DateTime  @default(now())
  updatedAt      DateTime  @updatedAt
  events         DealEvent[]

  @@index([userId, stage])
  @@index([userId, nextStepAt])
}

model DealEvent {           // история сделки (для робота и карточки)
  id     String   @id @default(cuid())
  dealId String
  deal   Deal     @relation(fields: [dealId], references: [id], onDelete: Cascade)
  kind   String   // created | stage | amount | next_step | note
  from   String?
  to     String?
  text   String?
  at     DateTime @default(now())

  @@index([dealId, at])
}

model SalesPlan {
  id         String   @id @default(cuid())
  userId     String
  user       User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  monthStart DateTime @db.Date // UTC-полночь 1-го числа локального месяца (как MonthlyGoal)
  amount     Float

  @@unique([userId, monthStart])
}
```

`Entity` получает обратную связь `deals Deal[] @relation("EntityDeals")`. Удаление аккаунта —
каскадом (проверить `auth-delete-coverage.test.ts`).

## Стадии и follow-up

| Ключ | Название | Шаг по умолчанию при входе в стадию |
|---|---|---|
| new | Новая | «связаться» через 2 дня |
| talks | Переговоры | «следующий контакт» через 5 дней |
| proposal | КП отправлено | «спросить ответ по КП» через 3 дня |
| contract | Договор/оплата | «проверить оплату» через 3 дня |
| won | Выиграна | шага нет |
| lost | Проиграна | шага нет |

- Срок, названный юзером («перезвонить во вторник»), всегда побеждает дефолт.
- Робот проговаривает назначенный шаг: «Напомню спросить ответ в понедельник (10.11)».
- Стадии можно перепрыгивать (сразу «договор») и возвращать назад; каждая смена — `DealEvent`.
- won/lost закрывают сделку: `closedAt`, `nextStepAt = null`. Повторное открытие = смена стадии на открытую.

Чистые функции (`services/deals/stages.ts`): `defaultNextStep(stage, today)`, `isOpen(stage)`,
`stageLabel`, `parseStage` (рус. синонимы: «кп», «предложение», «договор», «оплатил», «отказался»…).

## Инструменты робота (реестр tools)

- `create_deal` — «Ахмет хочет оборудование на 2 млн». Клиент через `resolveEntity`
  (`services/entity-graph`); нет сущности — создаётся person. Если у человека нет типа —
  ставим `client` и говорим об этом вслух («Ахмета отметил клиентом»).
- `update_deal` — стадия / сумма / следующий шаг / заметка / причина проигрыша.
  Сделку ищем по клиенту (+ название, если сказано). **Ровно одна открытая — меняем;
  несколько — переспрашиваем со списком; ноль — предлагаем завести.** Не угадываем.
- `list_deals` — «что у меня по сделкам?»: открытые по стадиям с суммами, шаги на сегодня/просрочка, план месяца.
- `set_sales_plan` — «план на ноябрь — 10 млн».

Роли без пересечений (дописать в описания + `tools/tool-roles.test.ts`):
- «отправил КП Ахмету» (сделал) → `update_deal`; «обещал прислать КП до пятницы» (обещание) → `create_obligation`.
- «перезвонить Ахмету во вторник» при открытой сделке с Ахметом → `update_deal` (шаг), иначе `create_task`.
- «получил 2 млн от Ахмета» при сделке на стадии contract → `update_deal` won + предложение дохода (не голый `add_income`, чтобы не задвоить).
  Детерминированно в оркестраторе (`routeIncomeToDeal`, ревью X1): маршрутизация **ничего не пишет**.
  Клиента ищем только точным матчем имени по словам среди открытых сделок (`matchDealsByMention`,
  без эмбеддингов: «Ахмед» ≠ «Ахмет»; «от клиента Даны», «от ТОО Альфа» — служебные слова пропускаем).
  Одна сделка и (стадия `contract` ИЛИ сумма совпала) → pending `record_deal_income {dealId, markWon, amount}`
  «закрыть как выигранную и записать доход …?»; на «Подтвердить» — `updateDeal(won, сумма если не было)` +
  `recordDealIncome`; «нет» — сделка как была, монет нет. Несколько сделок / другая сумма / ранняя стадия
  без суммы → переспрос. «аванс/предоплата/частично/первую часть» → обычный `add_income`, после «да» —
  заметка «аванс N ₸» в сделке, стадия не меняется. Сделка с уже записанным доходом (вернули в работу) →
  только «отметить выигранной?», без второго дохода.
  Переспрос всегда заканчивается «Или скажи «просто доход» — запишу обычным доходом»: сумма/источник
  хранятся в pending `deal_income_choice` (без кнопок, не отдаётся в `/voice/pending-action`); «просто доход»
  → обычный `add_income` на ту же сумму; «да» на переспрос — подсказка, ничего не пишем (ревью I-d).
  Двухшаговый ввод («получил 2 млн» → «от Серика») идёт тем же путём сделки.

Инструменты в ходе (ревью B1/I-b): `mayNeedLocalTools` знает корни сделок («тыс», «800к», «предложение»,
«счёт», «контракт», «подписал», «согласился», «перевёл», «скинул», «передумал»…, порог < 12 символов сохранён);
плюс `needsLocalTools` — при включённых сделках имя клиента с открытой сделкой в сообщении (падежи, имя ≥ 4 букв)
тоже включает инструменты («как там Ахмет по оборудованию?»).

Антифабрикация: сумма/стадия/срок только из слов юзера; сумма не названа → `amount = null`,
робот её не придумывает.

## Доход при выигрыше

- Через робота: смена на `won` при `amount != null` и `wonIncomeId == null` → `PendingAction`
  `record_deal_income` (как `apply_reschedule` в `runConfirmedAction`, не tool реестра):
  «Записать доход 2 000 000 ₸ от Ахмета?» [Подтвердить / Отмена].
- Через панель: кнопка «Записать доход» → `POST /deals/:id/income`.
- Оба пути зовут одну `recordDealIncome(userId, dealId)`: в транзакции создаёт `Income`
  (source «Сделка: Ахмет — оборудование», date = сегодня по tz) и ставит `wonIncomeId`;
  повтор — no-op «уже записан». Сумма не названа — дохода не предлагаем, робот просит сумму.
- Карточная правка не перезаписывает чужой pending (правило `fromCard`, как в reschedule).
- Подтверждение, поставившее новый вопрос (страховка «уже записан — ещё раз?»), отдаёт его в ответе
  (`pendingAction` + `confirmationText`; на `/voice/confirm-action` — `done: false`) → кнопки есть (ревью I-c).

## План продаж

`salesPace(plan, wonThisMonth, openSum, today)` — чистая:
- `won` = сумма сделок, закрытых `won` в этом локальном месяце; `open` = сумма открытых.
- «Отстаёшь»: с 7-го дня месяца `won < plan × (прошло_дней / дней_в_месяце) × 0.8`.
- Текст: «Закрыто 4 млн из 10, в работе ещё 7 — успеешь, если закроешь Ахмета и Серика»
  (называем крупнейшие открытые, покрывающие разрыв) или «в работе не хватает на план».
- Сделки без суммы в сумму не входят, робот говорит «у 2 сделок нет суммы».

## Проактивность (v2-proactivity-engine)

| source | Когда | significance | При спаде настроения |
|---|---|---|---|
| `deal_next_step_due` | открытая, шаг сегодня или просрочен < 3 дней; до 3 сделок в одном нудже | 0.6 (как obligation_due) | **выживает** — это обязательство клиенту |
| `deal_stale` | открытая и (шаг просрочен ≥ 3 дней ИЛИ `lastActivityAt` ≥ 7 дней и шага нет вообще); шаг сегодня/впереди — не «затихла»; раз в неделю на сделку | 0.6 | глушится (в `PRESSURE_SOURCES`) |
| `sales_plan_behind` | план есть и `salesPace` = отстаёшь; кулдаун неделя | 0.65 | глушится (в `PRESSURE_SOURCES`) |

`PRESSURE_SOURCES` растёт с 10 до 12 — обновить анти-регресс тест размера.
Дедуп/кулдаун (после ревью): `deal_next_step_due` — ключ `deals_due:<sha1 отсорт. id всех сделок «пора», 16 hex>:<дата юзера>` (новая сделка/новый день шага → новый нудж, повтор в тот же день — дедуп R10; просрочка ≥ 3 дней из набора уходит, так что «пора» не звучит вечно); `deal_stale` — `entityId = dealId`, недельный ритм держит детектор (`nudgedWithin` 6.5 дн на ключ сделки, смахнутые тоже считаем); `sales_plan_behind` — недельный ритм держит сам детектор (ряд `v2_nudge` с тем же scopeKey за 7 дней, включая смахнутые), т.к. `gate4_Dedup` не матчит формат scope стора (известная дыра, `TODO(gate4)`).
Нудж пишется в историю чата (как сейчас `deliverTopInsight`) → ответ «да» доходит до робота с контекстом.

## Связи с остальным

- **Бриф встречи** (`buildPersonMeetingBriefs`, person-types): если у человека открытая сделка —
  строка «сделка «оборудование» 2 млн, КП отправлено 4 дня назад, ответа нет».
- **Enrichment** (`v2-enrichment`, по образцу openLoops): блок «Сделки»: открыто N на сумму X,
  шаги сегодня/просрочено (имена), план месяца. READ-ONLY, только факты из БД.
- **Память**: смена стадии/заметка обновляет `lastSeenAt` клиента (как упоминание человека).
- **Обещания**: не связываем автоматически (решение: разные смыслы), но бриф показывает и то и другое.

## REST (для панели)

- `GET /deals?status=open|closed` — открытые по стадиям / закрытые за 90 дней.
- `POST /deals` · `PUT /deals/:id` (стадия, сумма, шаг, заметка, причина) · `GET /deals/:id` (с событиями).
- `POST /deals/:id/income` — записать доход (идемпотентно).
- `GET /sales-plan?month=YYYY-MM` · `PUT /sales-plan`.
- Все с `authMiddleware`, фильтр `userId` в каждом запросе (cross-user isolation it-тест).
- Правка руками = тот же сервис, что и инструменты; ответ на смену стадии содержит назначенный шаг.

## Мобилка (этап 2)

- Новый инструмент `deals` в `services/room-tools.ts`, дом — `desk` (стол), рядом с задачами.
  `robot-explain` получает панель `deals`.
- `stores/deal-store.ts` (zustand), `components/deals/*`:
  полоска плана месяца сверху → сделки, сгруппированные по 4 открытым стадиям (сумма по стадии) →
  «Закрытые» свёрнуто. Карточка: клиент, название, сумма, стадия (кнопки соседних стадий),
  шаг и дата, история, «Выиграна» / «Проиграна» (причина), «Записать доход».
  «+» — ручное добавление (клиент из списка людей или новый).
- `GET /deals` ответил 404 (флаг выключен) → инструмента «Сделки» на столе нет.
- Правки руками видны роботу (общая БД) и бампают `scheduleRevision`-подобный счётчик, чтобы
  панель перечитывалась после ответа робота.

## Флаг и выкатка

`FEATURE_V2_DEALS` (`isV2DealsEnabled`): off — инструменты отвечают «недоступно» (handler-гейт,
как новые тулзы), нуджи/enrichment/бриф без изменений (байт-идентично), REST → 404.
По правилу ship → all после ревью. Миграция аддитивная.

## Ошибки и края

- Несколько клиентов с похожим именем → `resolveEntity` + переспрос, не угадываем.
- Сделка без клиента («продал оборудование») → робот спрашивает «кому?».
- Валюта: только ₸ в v1 (поле есть на будущее).
- Часовой пояс: даты шага convA (`localDateOnlyUTC`), месяц плана — локальный месяц юзера.
- Сбой нуджа/enrichment — best-effort, ответ робота не ломает.

## Тесты

- Unit: `defaultNextStep`, `parseStage` (рус. синонимы), `salesPace` (границы 7-го дня, без сумм),
  выбор одной сделки (0/1/много), текст брифа/enrichment.
- Integration: create/update по голосу через реестр; переспрос при двух сделках; won → pending →
  confirm → Income ровно один раз (повтор no-op); REST CRUD + чужой userId → 404;
  нуджи due/stale/behind + глушение при спаде; бриф встречи со сделкой; флаг off = как раньше;
  удаление аккаунта чистит Deal/DealEvent/SalesPlan.
- Роли инструментов: КП-сделал vs обещал, перезвонить при сделке vs без, «получил деньги» при contract.
- Мобилка: store (группировка, оптимистичная смена стадии + откат), панель рендерится.

## Этапы

1. **Сервер**: схема+миграция → чистые функции → сервис (CRUD, события, доход) → инструменты и роли →
   REST → нуджи → enrichment и бриф → флаг. Коммит на шаг.
2. **Мобилка**: store → панель и карточка → инструмент на столе → robot-explain → сборка.

## Не делаем в v1

Команда/руководитель, свои стадии, вероятности и взвешенный прогноз, интеграции
(amoCRM, Bitrix24, WhatsApp, звонки), отчёты, мультивалюта, импорт сделок из Excel.
