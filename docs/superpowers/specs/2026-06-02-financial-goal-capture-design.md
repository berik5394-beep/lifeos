# Захват фин-цели — `suggest_goal` как единый умный захват цели (improvement)

**Дата:** 2026-06-02
**Статус:** утверждён Berik (brainstorm 2026-06-02, все 4 секции), готов к writing-plans
**Тип:** улучшение существующего инструмента (аддитивно, за флагом) — НЕ новый инструмент, НЕ rebuild
**Связь:** follow-up к коучу по накоплениям (#170, в проде). Живой SMOKE вскрыл дыру.

---

## Север (рамка, держит каждое решение)

Мы строим **живого друга** с **единой памятью+мозгом** (поэтому лучше Replika) и с **чувствами+проактивностью** (поэтому лучше Notion): он помнит, читает между строк, видит настроение и характер, **сам напоминает и сам записывает**. Постановка цели должна ощущаться как разговор с другом, который потом реально помнит и ведёт — а не как заполнение анкеты. Инструмент — мелкая крепкая часть; ум живёт в разговоре вокруг него и в том, что цель дальше живёт в одном мозге. Правило: не исполнять буквально кривое, тянуть к конечной цели.

## 1. Проблема (по фактам прод-БД)

SMOKE: «разбери цель накопить 100000 к концу месяца» → бот ответил разговором и **не вызвал ни один инструмент-сохранитель**. ToolCall = только `add_expense`+`get_today`. YearlyGoal 2026 = только «прочитать 50 книг» (career). Фин-цели с `target` нет → `gatherReflectorFacts.financeGoalTarget=null` → коуч молчит (правильно, ему нечего вести).

Корень: **нет пути, создающего `YearlyGoal{area:finance, target, targetDate}`.** `suggest_goal` создаёт цель, но его схема `{area, goalText, rationale}` — **без числа и срока**. `decompose_goal` число ловит, но он для дерева год→недели, и бот сам его избегает для накоплений. Плюс поведенческое: бот **нарративит вместо вызова**.

## 2. Решение (Подход 1, сделанный «вдолгую»)

`suggest_goal` становится **единым умным захватом цели**: одна голова, без новых инструментов (28 целы), на проверенной инфре (confirm-FSM + создание YearlyGoal = не ломается). Ум — в разговорном слое вокруг, переиспользующем мозг.

### Секция 1 — ядро инструмента
- **Схема +2 опц. ОБЩИХ поля** (не только финансы): `target?: number` (величина: 100000, «50 книг»), `targetDate?: string` (дата `YYYY-MM-DD` или относительная «к концу месяца»/«к декабрю» → резолвим готовым `parseGoalDeadline(text, now)`).
- **Хендлер — idempotent create-or-update** (закрывает «правку», не плодит дубли):
  - `goalId` передан → обновляем эту цель;
  - иначе за год ищем цель той же `area` с похожим текстом (паттерн planner: `goalText contains` первых ~60 симв.) → нашли → **обновляем** `target`/`targetDate`/текст; не нашли → **создаём**.
  - Логика разделения вынесена в ЧИСТЫЙ хелпер `decideGoalWrite(existing, input) → {mode:'create'|'update', goalId?}` (тестируется без БД).
  - Семантика: «накопить 100к к месяцу» и «накопить 3 млн за год» — разный текст → две цели; «цель теперь 150к»/«передвинь срок» → апдейт.
- **Confirm-preview**: кейс для `suggest_goal` в `confirmationText` (jarvis-orchestrator:306) — «Записать цель: накопить 100 000 ₸ к 30 июня?» / «Обновить цель: срок → 31 августа?». Юзер видит сумму+срок до подтверждения.
- `needsConfirm: true` остаётся.

### Секция 2 — разговорный ум (почти всё reuse мозга)
- **Записывает, а не болтает:** усиление `jarvis-prompt.ts` — услышал цель с суммой/сроком → **оформляет через `suggest_goal`** (тёплое подтверждение), совет поверх записи, не вместо. + описание/examples инструмента под «поставь/хочу цель накопить X к Y».
- **Читает между строк:** существующий inline-nudge (jarvis-prompt:27-34 «оформить скрытое намерение в цель») дотачиваем под измеримое/накопления: «хочу на машину» → бот сам предлагает «оформлю как цель — на сколько и к сроку?».
- **Доспрашивает по-дружески:** цель измеримая, но нет суммы/срока → один живой вопрос, потом запись (не форма, не падение).
- **Чувствует настроение/характер — REUSE:** `therapeutic-mode` (выговаривается/грустит → НЕ навязывать цель), `assistantStyle` (тон предложения), эмоц-память/axes (момент и тон). Новой подсистемы НЕ строим.
- **Тёплое подтверждение + вплетает:** на «да» — по-дружески + связь с контекстом + цель ложится в единый мозг → бот вспомнит её сам потом.

### Секция 3 — правка + проактивное предложение
- **Правка** — это idempotent update из Секции 1. Чтобы бот точно нашёл цель: в контекст промпта (там уже «Годовые цели: …», jarvis-prompt:181) добавить **id+сумму+срок** активных целей → бот ссылается на `goalId`. Confirm на апдейт.
- **Проактивно (друг сам напомнит):**
  - внутри разговора — nudge из Секции 2;
  - отдельным сигналом — **reuse v2-proactivity**: детектор «в памяти есть накопительное намерение, но оформленной фин-цели нет» → в брифинге мягко «ты говорил про машину — оформим как цель?». За тем же ≤1/день гейтом, best-effort. (Если на реализации окажется рискованно/дорого — выносим детектор в отдельный follow-up; ядро Секций 1-2 самодостаточно.)

### Секция 4 — флаг, тесты, замыкание
- **Флаг:** тот же `FEATURE_V2_SAVINGS_COACH` (одна история: поставил цель → коуч ведёт; один флаг — вся петля). Off → `suggest_goal` как сегодня: схемные поля аддитивны и безвредны; новое поведение хендлера (create-or-update + запись target/targetDate) и промпт-усиление — **за флагом** (`isV2SavingsCoachEnabled(ctx.userId)`), off = байт-в-байт.
- **Тесты:** unit `decideGoalWrite` + `parseGoalDeadline` (уже есть); структурные (схема несёт target/targetDate; confirmationText-кейс; промпт-инструкция «записывай измеримую цель»; флаг-гейт в хендлере); e2e на уровне реестра: вход «накопить 100к к концу месяца» → normalize+parse → handler-намерение create с target=100000+targetDate. Существующий `suggest_goal` тест остаётся зелёным (без регресса).
- **Замыкание петли (главное доказательство):** SMOKE-сценарий, который провалился, проходит end-to-end — поставил цель → `YearlyGoal{finance,target:100000,targetDate}` в БД → расход → реактивная строка коуча. По факту БД.

## 4. Не-цели / YAGNI

- НЕ новый инструмент (улучшаем `suggest_goal`); НЕ трогаем коуч (он готов и в проде).
- НЕ строим заново настроение/проактивность/память — **переиспользуем** (один мозг).
- НЕ Decimal, НЕ мобильный UI (слой представления — при сборке приложения).
- Проактивный детектор (Секция 3) — может стать отдельным follow-up, если на реализации дорого/рискованно; ядро (Секции 1-2-4) самодостаточно закрывает SMOKE-дыру.

## 6. IMPLEMENTATION NOTE (2026-06-02) — дизайн эволюционировал при сборке

Глубинная находка при кодировании (фиксирую честно): **`suggest_goal` был недостижим из чата.** `needsConfirm:true` исключал его из набора агента (`agentToolSchemasForUser` фильтрует needsConfirm) — это и есть истинный корень SMOKE (цель не предлагалась/не сохранялась), глубже «нет поля».

Поправка Berik: **бот НЕ пишет без «да» — спрашивает.** Финальная схема (паттерн денег propose→confirm→write):
- **`suggest_goal` = агент-вызываемый ПРЕДЛОЖИТЕЛЬ** (`needsConfirm:false`, но САМ не мутирует): ставит `setPendingAction('commit_goal', …)` + возвращает дружеский вопрос. Достижим из чата; деньги-инвариант цел (не пишет).
- **`commitGoal` (services/goal-commit.ts)** — реальная запись на «да»: `runConfirmedAction` ветка `commit_goal` (как `run_skill_actions`). create-or-update (`decideGoalWrite`) + резолв срока + `target`/`targetDate`.
- **Промпт** `GOAL_CAPTURE_BLOCK` (buildJarvisPrompt `opts.goalCapture`, за `isV2SavingsCoachEnabled`): читай между строк → предложи через suggest_goal с target+срок. Off → байт-в-байт.
- Замена пункта «confirmationText case»: вопрос строит сам предложитель (возвращает его), отдельный кейс в `confirmationText` не нужен.
- Проактивный детектор (Секция 3, отдельный сигнал) — **отложен** как осознанный follow-up; ядро (предложение-в-разговоре + правка + запись) закрывает SMOKE-дыру.

Источник правды по коду — сами файлы + их комментарии. Сюита 2064 зелёная, tsc 0.
